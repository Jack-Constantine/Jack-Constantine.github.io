# 实习Intern 入职学习与能力沉淀手册

> 职业目标：从交易/数据后端，逐步成长为“懂业务、懂系统、懂 Agent 与部分算法”的 AI 研发工程师  
---

## 0. 这份手册要帮我完成什么

这段实习的核心目标，不是把“后端经历”强行包装成“算法经历”，而是在完成本职工作的基础上，逐步获得下面这条完整能力链：

```text
真实业务问题
→ 业务对象与约束建模
→ 生产系统与数据链路
→ Agent 的工具和交互环境
→ 任务、轨迹与反馈数据
→ 评测、Verifier 与 Bad Case
→ Prompt / Tool / Data / Model 策略迭代
→ 线上效果和业务价值
```

实习结束时，我希望自己能够被描述为：

> 做过真实交易与数据系统，能和策略人员定义问题，能把业务能力封装成 Agent 工具，能搭任务、轨迹、评测和反馈闭环，并理解这些资产如何进一步用于 Agent Post-training 或 Agentic RL。

# 第一部分：合规边界——什么可以学，什么不能带走

## 1.1 最重要的原则

我应该带走的是：

- 解决问题的方法；
- 对业务和系统的理解方式；
- 需求拆解、实验设计和故障归因能力；
- Agent 工具、任务、评测和反馈闭环的设计思想；
- 与产品、策略、算法和研发协作的方法；
- 自己经过实践形成的判断力。

我不能带走的是：

- 公司内部文档原文、截图、录屏；
- 源代码、SQL、接口定义和配置文件；
- 服务名、表名、字段名、内部域名和拓扑；
- 交易数据、行情数据、用户数据和策略数据；
- 内部 Prompt、System Prompt、模型参数和评测集；
- 线上指标、业务规模、故障细节和未公开产品规划；
- 任何账号、密钥、Token、Cookie 或访问凭证。

一句话：

> 内部事实留在公司；通用原理进入大脑；公开展示必须重新实现。

## 1.2 三层笔记隔离

| 层级 | 可以写什么 | 存在哪里 | 能否带走 |
|---|---|---|---|
| 内部工作笔记 | 真实服务名、接口、字段、内部指标、任务细节 | 公司授权系统 | 否 |
| 个人能力笔记 | 去标识化的方法、抽象流程、自己对原理的解释 | 经公司制度允许的个人学习载体 | 仅限不含机密的抽象知识 |
| 公开项目 | 使用公开数据、开源代码重新实现的方法 | 个人 GitHub/博客 | 是，但不得复用内部资产 |

如果不能确定某项内容是否可记录或公开，默认不记录、不上传，并询问导师或主管。

特别注意：未经明确许可，不把内部信息输入个人 ChatGPT、Claude、Cursor、Copilot 或其他外部模型。

7. 策略研究与实验流程；

9. 历史方案、技术选型和失败实验；
10. 代码评审、发布和回滚规范。

我读完一篇文档，不能只留下“看懂了”的感觉，而要产出一种可以检查的理解结果。

## 2.2 团队介绍、业务词汇表与系统地图

### 要找的材料

- 新人 Onboarding；
- 团队职责介绍；
- 业务 Glossary；
- 系统全景图；
- 团队分工和服务负责人；
- 上下游合作方介绍。

### 读完必须回答

1. 团队服务的最终用户是谁：策略研究员、运营、交易执行人员，还是其他系统？
2. 团队最重要的三个业务目标是什么？
3. 哪些模块属于本团队，哪些属于上下游？
4. 一个需求通常由谁提出、谁评审、谁上线、谁验收？
5. 哪些系统是核心链路，哪些是辅助链路？
6. 哪些词在公司语境中有特殊含义？

### 企业现实示例

假设文档中出现“行情延迟”“订单状态”“策略回放”“数据修订”几个词。初学者容易只记定义，但真正要理解的是它们之间的关系：

```text
行情数据到达晚
→ 策略读取到的市场状态落后
→ 生成的决策可能基于旧信息
→ 下游订单行为和回放结果出现差异
→ 研究人员无法复现实验
```

应该进入大脑的不是某个内部服务名，而是：

> 在实时决策系统里，数据的新鲜度、顺序和可追溯性直接决定策略行为是否可信。

### 我的理解产物

不记录内部名称，只在脑中和合规笔记中形成这样的抽象图：

```text
数据源 → 接入 → 清洗 → 标准化 → 存储/推送
                          ↓
                    策略研究/实时计算
                          ↓
                    订单/执行/回报
                          ↓
                    归档/分析/复盘
```

## 2.3 核心业务流程与状态机文档

### 要找的材料

- 行情处理流程；
- 订单生命周期；
- 交易或任务状态机；
- 异常重试、撤销、补偿流程；
- 权限、风控、人工介入机制；
- 离线回放和线上运行差异。

### 读完必须回答

1. 核心业务对象有哪些？
2. 每个对象有哪些合法状态？
3. 什么事件触发状态转换？
4. 哪些事件可能重复、乱序、迟到或丢失？
5. 系统如何保证幂等？
6. 哪些操作不可逆？
7. 哪些异常必须人工确认？
8. 哪些约束必须由代码保证，而不能只依赖 Prompt 或模型？

### 企业现实示例：重复事件

假设上游因为网络超时，没有收到确认，于是把同一条事件重发了一次。如果下游只看“收到了事件”就执行，可能导致重复处理。

企业系统不会只要求“正常请求能成功”，还要求：

```text
同一个业务事件重复到达两次
→ 系统识别业务唯一键
→ 第二次执行不产生额外副作用
→ 返回与第一次一致的可解释结果
```

应该带走的能力是：

> 设计业务接口时，要先问“如果它重复、乱序、超时、部分成功，会发生什么”，而不是只写正常路径。

这项能力以后会直接迁移到 Agent：Agent 经常重复调用工具、在超时后重试，工具必须具备幂等性和明确的状态语义。

## 2.4 数据字典、数据血缘与指标口径文档

### 要找的材料

- 表和字段的数据字典；
- 实时与离线数据链路；
- 数据生产者和消费者；
- 数据延迟、完整性和质量规范；
- 指标定义；
- 数据修订和版本管理；
- 数据权限和脱敏规则。

### 读完必须回答

1. 每个关键字段的业务含义是什么？
2. 字段由谁生产，经过哪些处理，最终被谁使用？
3. 事件时间、处理时间和落库时间有什么差异？
4. 数据是否会修订？修订后如何追溯？
5. 缺失值、异常值和迟到数据如何处理？
6. 同名指标在不同系统里口径是否相同？
7. 离线训练/回测数据和线上数据是否存在偏差？

### 企业现实示例：指标名字一样，口径不一样

两个报表都叫“成功率”：

- 报表 A：成功请求数 / 收到的请求数；
- 报表 B：最终成功的业务任务数 / 去重后的有效任务数；
- 报表 C：用户没有人工纠正的任务数 / 所有完成任务数。

三个数字可能差别很大，却都没有计算错误。

应该带走的能力是：

> 看到一个指标，先问分子、分母、去重方式、时间窗口、过滤条件和异常样本，而不是直接比较数字。

以后做 Agent Evaluation，同样不能只写“成功率提升 10%”，必须解释任务集合、成功判定和失败样本如何处理。

### 企业现实示例：数据泄漏

策略研究员使用了一列“任务最终状态”训练或验证模型，但该字段只有任务结束后才生成。离线效果可能很好，线上却无法使用。

应该进入大脑的是：

> 任何训练特征、Agent Observation 或评测输入，都必须确认在决策发生时是否真实可见。

这既是交易研究中的未来信息泄漏，也是 Agent 训练中的环境信息泄漏。

## 2.5 系统架构、RFC 与技术选型文档

### 要找的材料

- 系统架构图；
- 核心模块 RFC；
- 存储、消息队列、缓存、RPC 选型；
- 同步/异步设计；
- 一致性和容错策略；
- 历史重构方案；
- 被否决方案和评审意见。

### 读完必须回答

1. 系统边界在哪里？
2. 每个模块的输入、输出和责任是什么？
3. 为什么采用当前方案，而不是更简单的方案？
4. 系统优先优化延迟、吞吐、一致性、成本还是开发效率？
5. 哪些依赖一旦故障会影响核心链路？
6. 系统怎样降级、限流、重试和恢复？
7. 当前设计最大的技术债是什么？

### 企业现实示例：为什么不能把所有逻辑放进一个服务

一个“方便”的设计可能把数据查询、策略计算、任务执行、结果写入都放在同一请求里。但现实中：

- 数据查询可能很慢；
- 策略计算可能超时；
- 写入成功但响应丢失；
- 重试可能导致重复执行；
- 某个依赖故障拖垮整个服务。

成熟设计可能采用任务状态、异步队列、幂等执行和结果回查。

应该带走的能力是：

> 架构不是为了“看起来高级”，而是把不同失败模式隔离，让系统在部分失败时仍然可控。

这项能力以后能帮助我设计 Agent Harness：模型生成、工具执行、环境状态、评测和人工确认也不应混成一个不可追踪的黑盒。

## 2.6 API、Schema、代码入口与测试文档

### 要找的材料

- API 文档；
- Protobuf/IDL/Schema；
- 关键代码目录说明；
- 单元测试和集成测试规范；
- Mock/回放环境；
- 发布、灰度和回滚流程；
- Code Review 规范。

### 读完必须回答

1. API 表达的是技术动作还是业务语义？
2. 输入有哪些前置条件？
3. 错误码是否可区分重试、拒绝和永久失败？
4. 请求是否幂等？
5. Schema 如何演进和兼容旧版本？
6. 哪些逻辑由单元测试覆盖，哪些必须集成测试？
7. 上线后怎样快速发现和回滚问题？

### 企业现实示例：错误信息决定 Agent 能否恢复

下面两种工具返回对人类看起来都算失败：

```json
{"success": false, "message": "执行失败"}
```

```json
{
  "success": false,
  "error_type": "INVALID_TIME_RANGE",
  "retryable": false,
  "invalid_fields": ["start_time", "end_time"],
  "hint": "start_time must be earlier than end_time"
}
```

第二种返回能让 Agent 修正参数并继续执行，第一种只能让它猜。

应该带走的能力是：

> Tool/API 的可学习性和可恢复性，取决于稳定 Schema、明确错误分类和可执行反馈，而不只是接口能否调用。

## 2.7 监控、SLO、告警和故障复盘文档

### 要找的材料

- 服务 SLO/SLA；
- Dashboard；
- 告警规则；
- On-call 手册；
- 故障复盘；
- 容量评估；
- 灰度和回滚记录。

### 读完必须回答

1. 系统真正重要的三个指标是什么？
2. 哪些指标是结果指标，哪些是提前预警指标？
3. 告警触发后第一步看什么？
4. 最近几次事故的共同原因是什么？
5. 为什么测试没有提前发现？
6. 修复的是表面问题还是系统性原因？
7. 如何确认修复没有引入新问题？

### 企业现实示例：平均延迟看起来正常，但用户已经受影响

平均延迟可能是 20ms，但少量任务因为某个依赖超时达到 5s。平均值变化不大，P99 和超时率却显著恶化。

应该带走的能力是：

> 面对有长尾的系统或 Agent，不只看平均值；要看分位数、失败分布、任务难度和关键子群体。

以后评测 Agent 时，也要按轨迹长度、工具数、任务类型和失败类型拆分，而不是只看总体成功率。

### 企业现实示例：事故复盘不是找人背锅

一次错误发布造成任务积压。表面原因是工程师配置错误，更深层原因可能是：

- 配置没有 Schema 校验；
- 灰度范围过大；
- 告警只监控机器，没有监控业务积压；
- 回滚需要人工执行多个步骤；
- 测试环境无法复现真实流量。

应该带走的能力是：

> 高质量复盘要找到“为什么一个人的一次普通错误能够穿透所有防线”，并修复系统，而不是只提醒以后小心。

## 2.8 策略研究、实验和工程化文档

### 要找的材料

- 策略需求说明；
- 实验设计；
- 特征和数据版本；
- 回测或离线验证规范；
- 策略上线流程；
- 研究代码到生产代码的迁移规范；
- 实验追踪和复现说明。

### 读完必须回答

1. 策略团队真正要解决什么问题？
2. 输入、输出和业务约束是什么？
3. Baseline 是什么？
4. 离线指标为什么能代表线上价值？
5. 实验是否可复现？
6. 如何避免数据泄漏、选择偏差和过拟合？
7. 研究代码怎样进入生产系统？
8. 上线后如何监控策略漂移？

### 企业现实示例：需求不是“帮我做个接口”

策略同学提出：“帮我做一个查询历史数据并运行分析的接口。”

低质量理解：

> 按输入条件查数据，然后返回结果。

高质量理解需要继续问：

- 数据按事件时间还是处理时间查询？
- 是否包含后续修订数据？
- 同一次实验怎样固定数据版本？
- 大查询如何限流？
- 任务失败能否断点恢复？
- 结果如何追溯到代码、参数和数据版本？
- 不同实验怎样公平比较？

应该带走的能力是：

> 研发的价值不是机械实现需求，而是把模糊研究过程变成可复现、可验证、可上线的系统能力。

这正是“懂业务又懂算法”的研发工程师与普通接口开发的区别。

## 2.9 Agent 任务定义、工具、轨迹和评测文档

如果团队存在 Agent 项目，这部分是职业转型的重点。

### 要找的材料

- Agent PRD/任务定义；
- Prompt 与上下文构造说明；
- Tool Schema；
- Planner/Executor/Memory 设计；
- Agent 轨迹格式；
- 测试集和 Benchmark；
- 自动评估和人工评审规范；
- Bad Case 分类；
- 模型、Prompt、工具版本对比实验；
- 权限、安全和人工接管方案。

### 读完必须回答

1. 为什么这里需要 Agent，而不是固定 Workflow？
2. Agent 的状态、动作和观察分别是什么？
3. 哪些动作由模型决定，哪些必须由规则限制？
4. 工具是否只读？哪些操作需要审批？
5. 一条完整轨迹如何记录和重放？
6. 什么叫成功？谁来判断？
7. 当前最大的失败类型是什么？
8. 是模型不会，还是工具/环境/上下文设计有问题？
9. 离线评测和线上业务效果是否一致？
10. 轨迹数据能否用于 SFT、Reward 或 RL？

### 企业现实示例：不是所有问题都该用 Agent

任务：每天固定时间读取一张表，运行同一个 SQL，把结果推送给固定人员。

这更适合 Workflow，因为：

- 步骤固定；
- 没有动态决策；
- 输入结构稳定；
- Agent 只会增加成本和不确定性。

任务：策略人员提出开放问题，系统需要判断查询哪些数据、执行哪些分析、根据中间结果决定下一步，并最终给出带证据的结论。

这才可能需要 Agent，因为：

- 路径不固定；
- 需要多轮观察和决策；
- 不同问题使用不同工具；
- 中间结果决定下一步。

应该带走的能力是：

> 先判断任务是否真的包含决策和环境反馈，再决定是否使用 Agent。

## 2.10 历史方案、失败实验与 Code Review

### 要找的材料

- 被废弃的设计；
- 历史重构 RFC；
- 性能优化前后对比；
- 实验失败报告；
- 典型 Code Review；
- 线上问题修复 PR。

### 为什么它们特别重要

最终代码只告诉我“现在是什么”，历史材料告诉我：

- 以前为什么不行；
- 团队为哪些约束付出过代价；
- 哪些直觉在真实环境里失败；
- 有经验的人如何权衡。

### 企业现实示例：模型更强，业务结果却变差

团队升级了模型，离线通用能力更强，但线上任务成功率下降。可能原因不是“新模型不好”，而是：

- Tool Call 格式发生变化；
- 输出更长导致超时；
- 更爱自主探索，调用成本上升；
- 对内部术语理解发生漂移；
- 原有 Prompt 针对旧模型过拟合；
- 自动 Judge 偏好长答案，但用户更需要可执行结果。

应该带走的能力是：

> 模型指标、Agent 指标和业务指标是三层不同的东西；任何升级都要经过端到端回归评测。

# 第三部分：实习结束最应该“带走”的七种能力

## 3.1 业务建模能力

不是记住业务名词，而是能够把一个模糊问题变成：

```text
目标
输入
输出
约束
状态
动作
反馈
失败条件
验收指标
```

### 具体例子

模糊需求：

> 做一个 Agent，帮助策略人员分析数据。

建模后的需求：

- 用户：策略研究员；
- 输入：自然语言研究问题和允许访问的数据范围；
- 动作：查 Schema、查询数据、生成代码、运行分析、检查结果；
- 环境：固定数据快照和隔离代码沙箱；
- 输出：结论、证据、代码、数据版本和实验记录；
- 成功：分析可执行、结论有证据、结果可复现；
- 约束：只读数据、禁止访问未来数据、限制计算资源；
- 失败：SQL 错误、代码异常、结论与结果不一致、引用不存在的数据；
- 指标：任务成功率、人工修改次数、复现率、平均工具调用和成本。

当我能完成这种转换时，我已经在做算法研发前端最重要的“问题定义”。

---

## 3.2 系统边界与失败模式思维

我要形成下意识的问题清单：

- 会不会重复？
- 会不会乱序？
- 会不会超时？
- 会不会部分成功？
- 能不能重试？
- 是否幂等？
- 如何回滚？
- 如何追踪？
- 谁负责最终一致？
- 错误发生后模型/用户能否知道下一步？

这套思维以后会直接迁移到 Agent Tool 和 Environment 设计。

---

## 3.3 从研究需求到生产能力的转化能力

策略人员可能提供一个 Notebook，但生产系统需要补齐：

- 稳定输入输出；
- 参数校验；
- 数据版本；
- 资源限制；
- 并发控制；
- 错误处理；
- 日志和监控；
- 单元和集成测试；
- 灰度、回滚和权限。

应该带走的不是“我帮策略团队写了接口”，而是：

> 我学会了如何把一个实验性算法封装成可复现、可监控、可迭代的生产能力。

---

## 3.4 Agent 工具与环境设计能力

真正有价值的能力包括：

- 工具粒度如何选择；
- Schema 如何让模型理解；
- 错误如何结构化；
- 哪些工具只读，哪些需要审批；
- 环境如何 Reset 和重放；
- 状态如何保存；
- 工具失败后如何恢复；
- 如何避免 Agent 重复执行和越权。

### 具体例子：工具粒度

过粗的工具：

```text
do_research(question)
```

模型无法学习中间决策，也难以诊断失败。

过细的工具：

```text
read_one_cell()
move_cursor()
append_one_character()
```

轨迹过长，错误累积严重。

更合理的工具可能是：

```text
inspect_schema(dataset)
query_data(query_spec)
run_analysis(code, data_snapshot)
validate_result(result_id)
compare_experiments(run_ids)
```

要带走的是选择粒度的判断方法，而不是某个内部工具的名字。

---

## 3.5 Evaluation、Verifier 与 Bad Case 能力

这是我从后端走向 Agent 算法研发最现实的桥梁。

我要学会：

- 构造有代表性的任务集；
- 定义可重复的成功判定；
- 将最终失败定位到具体步骤；
- 区分模型问题、数据问题、工具问题和环境问题；
- 设计自动评估与人工评估；
- 防止指标被模型投机；
- 对比离线指标和线上业务效果。

### 具体例子：Agent 最终答案错了，不能只记“回答错误”

应该继续定位：

```text
问题理解是否正确？
→ 计划是否覆盖必要步骤？
→ 是否选择了正确工具？
→ 参数是否正确？
→ 工具返回是否完整？
→ 模型是否正确理解 Observation？
→ 是否过早停止？
→ 结论是否得到证据支持？
```

只有这种粒度的归因，才能决定下一步应该改 Prompt、工具、数据还是模型。

---

## 3.6 数据和反馈闭环能力

我要理解一条线上任务如何变成可用于优化的训练资产：

```text
业务任务
→ Agent 轨迹
→ 自动与人工评测
→ 失败分类
→ 挖掘高价值样本
→ 修正工具/Prompt
→ 构造 SFT、Preference 或 RL 数据
→ 回归测试
→ 灰度上线
```

即使我没有直接训练模型，只要参与了任务、轨迹、评测和数据闭环，就已经具备 Agent Post-training 岗位非常需要的能力。

---

## 3.7 跨角色沟通与技术决策能力

我要学会使用不同语言与不同角色沟通：

- 对策略人员：讨论实验、数据、指标和复现；
- 对产品/业务：讨论用户价值、成功标准和风险；
- 对后端研发：讨论接口、状态、一致性和性能；
- 对算法人员：讨论数据、模型、Reward、评测和 Bad Case；
- 对主管：讨论优先级、资源、收益和交付风险。

最终要带走的是：

> 能把一个业务问题翻译成算法任务，又能把算法方案翻译成工程交付。

# 第四部分：三个完整企业场景示例

以下均为通用化假设示例，不代表公司实际实现。

## 4.1 场景一：数据 Pipeline 偶发缺失

### 表面任务

修复一个偶发数据缺失问题。

### 初级做法

- 找到报错；
- 增加一次重试；
- 确认数据重新生成；
- 关闭任务。

### 应该深入学习的内容

1. 缺失是生产端没产生，传输中丢失，还是消费端忽略？
2. 任务使用事件时间还是处理时间？
3. 重试是否会重复写入？
4. 补数据后，下游是否自动重新计算？
5. 下游策略是否已经使用了不完整数据？
6. 是否有完整性指标提前发现？
7. 为什么监控没有覆盖这个失败模式？

### 应该进入大脑的抽象模型

```text
生产完整性
× 传输可靠性
× 消费幂等性
× 数据版本
× 下游补偿
× 可观测性
= 一条可信的数据链路
```

### 如何迁移到 Agentic RL

Agent 轨迹也可能缺步骤、重复工具调用或因环境超时中断。因此需要：

- trajectory_id 和 step_id；
- 工具调用幂等；
- 明确 termination reason；
- 环境版本；
- 可重放轨迹；
- 失败步骤标记。

这就是从数据工程问题抽象出的 Agent 训练数据能力。

---

## 4.2 场景二：策略研究 Agent 的结果不可复现

### 表面现象

Agent 昨天得出一个结论，今天对同一个问题运行却得到不同结果。

### 不能只说“模型有随机性”

要依次检查：

- 使用的数据快照是否相同；
- Query 是否被改写；
- 检索结果是否变化；
- 工具版本是否变化；
- 代码执行环境是否变化；
- 模型、Prompt、采样参数是否变化；
- 是否保存每一步 Observation；
- 最终报告是否引用了真实执行结果。

### 成熟方案

一次实验至少绑定：

```text
task_version
data_snapshot
model_version
prompt_version
tool_version
environment_version
random_seed（适用时）
trajectory
verifier_result
```

### 应该带走的认知

> Agent 的可复现性不是模型参数一个人的问题，而是任务、数据、工具、环境和评测的联合版本问题。

### 面试时可以怎么讲

不能说内部实现，但可以讲通用方法：

> 我在真实数据/策略协作中意识到，Agent 结果的可复现需要绑定任务、数据快照、工具和模型版本，因此在公开项目中设计了可重放轨迹与版本化评测机制。

---

## 4.3 场景三：Agent 离线成功率提高，线上人员却不愿意用

### 表面数据

- 离线任务成功率：从 60% 提升到 75%；
- 线上使用率：没有提高；
- 用户仍然大量人工修改。

### 可能原因

- 离线任务太干净；
- 成功判定只看最终格式；
- Agent 结论正确但没有证据；
- 输出太慢；
- 调用了昂贵或不稳定工具；
- 用户真正需要可编辑的中间产物；
- Agent 对高价值困难任务效果差；
- 自动 Judge 与专业人员偏好不一致。

### 进一步建立的指标

- 人工修改率；
- 用户接受率；
- 任务完成时间；
- 证据正确率；
- 高价值任务成功率；
- 无效工具调用率；
- 人工接管点；
- 用户第二次使用率。

### 应该带走的认知

> 模型分数、Agent 任务成功率和业务价值不是同一个指标。算法迭代必须贯通离线评测、用户行为和业务结果。

这正是“懂业务又懂算法”的核心含义。

# 第五部分：让我真正理解并进入脑子的学习方法

## 5.1 不以“看过”为完成标准

一篇文档只有在完成以下动作后才算学会：

1. 不看原文，复述它解决的问题；
2. 画出输入、输出、状态和依赖；
3. 解释一个正常路径和两个异常路径；
4. 说清设计中的主要权衡；
5. 能定位代码入口和监控入口；
6. 能提出一个合理的改进问题；
7. 在实际任务中使用过至少一次。

## 5.2 每篇重要文档使用“五问法”

```text
1. 它解决了什么真实问题？
2. 为什么原来的方案不够？
3. 当前方案依赖哪些前提？
4. 最容易在哪些情况下失败？
5. 如果规模扩大十倍或接入 Agent，哪里先出问题？
```

## 5.3 用“反事实”检验理解

读完一个方案后问：

- 如果没有消息队列会怎样？
- 如果取消幂等键会怎样？
- 如果数据迟到 10 分钟会怎样？
- 如果工具返回模糊错误会怎样？
- 如果 Agent 连续调用五次同一工具会怎样？
- 如果自动评估规则被模型发现会怎样？

能回答这些问题，才说明理解了设计，不是只记住名词。

## 5.4 用“小任务”完成知识闭环

理解系统最有效的方法不是继续读，而是完成一个小修改：

- 增加一个指标；
- 补一个异常测试；
- 修一个错误码；
- 增加一次轨迹字段；
- 给工具补参数校验；
- 给 Benchmark 增加一种失败类型；
- 写一个重放脚本；
- 复现一个历史 Bad Case。

每次修改都要回答：

```text
修改前为什么不行？
修改了哪一层？
怎样证明修好了？
是否影响其他路径？
怎样监控它以后不再发生？
```

## 5.5 每周做一次“给外行讲明白”

选择本周最重要的一个主题，用不含内部名称的方式解释：

- 这个问题为什么难；
- 系统怎样解决；
- 主要权衡是什么；
- 失败时如何发现；
- 这项能力如何迁移到其他系统或 Agent。

如果离开内部术语就不会讲，说明还没有真正理解。

# 第十部分：最终要形成的简历叙事

不要说：

> 在滴滴做后端，平时也学习大模型和强化学习，希望转算法。

应该形成这样的事实链：

> 在真实交易/策略业务中负责核心数据或服务模块，理解高可靠数据链路与策略工程化；随后参与 Agent 场景，将业务能力封装成可控工具，建设任务、轨迹、自动评测和 Bad Case 闭环，并通过公开数据项目进一步完成 Agent Post-training/RLVR 实验。因此，我既能理解业务约束，也能完成从环境、数据、评测到模型策略优化的研发链路。

简历描述模板：

```text
面向【抽象业务场景】负责【系统/模块】，解决【一致性、延迟、复现或质量问题】，通过【技术动作】使【经批准可披露的指标】得到改善；协同策略/算法团队将【研究需求】转化为【可复现、可评测的工程能力】。

参与【Agent任务】建设，设计【工具/环境/轨迹/评测】并建立【指标和失败分类】；针对【典型Bad Case】通过【数据、工具、Prompt或模型策略】完成优化，使【经批准可披露的指标】改善。
```

任何指标、业务名和技术细节都必须经过公司允许后才能对外使用。

# 最后一页：每天提醒自己

1. 先把本职后端工作做好，信用是获得核心任务的前提。
2. 不只问“代码怎么写”，还问“业务为什么需要它”。
3. 不只看正常路径，重点看重复、乱序、超时和部分失败。
4. 不只看架构文档，重点看故障复盘、Bad Case 和失败实验。
5. 不只调用 Agent 框架，争取负责工具、环境、轨迹或评测。
6. 不只看最终成功率，要定位失败发生在哪一步。
7. 不为了转型强行使用 RL；先建立任务、环境、反馈和评测。
8. 内部事实留在公司，通用方法进入大脑，公开项目重新实现。
9. 每周形成一个能够脱离内部术语讲清楚的通用认知。
10. 实习结束时，我要能连接业务、系统、Agent 和算法，而不是只积累一行公司名称。
