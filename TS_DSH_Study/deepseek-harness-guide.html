CHAPTER 01

读源码前的语法补课

先掌握后面实际会遇到的写法。每小节先看可运行的小例子，再定位仓库里的用法。

上一份 TypeScript 从第一行开始 已经讲过对象解构、交叉类型、字面量联合、keyof、infer、satisfies 和异步迭代。本章在这些基础上继续。下面的「练习」块可以单独运行。「仓库摘录」默认显示带中文注释的阅读版。点击「看原文」可切回同一行号范围的原始代码。摘录可能只包含函数的一部分。JSONC 配置含阅读注释，JSONL 日志会把每条事件展开成多行。复制配置或日志原文时，先切换到原文。

1. import.meta 与入口保护

import.meta 是模块元信息。import.meta.url 给出当前模块的 URL，可用 new URL("./x", import.meta.url) 相对文件定位资源。它和随启动目录变化的 process.cwd() 解决不同问题。支持 import.meta.main 的 Node 版本还可以用它区分入口和被导入的模块。顶层 await 让直接入口等待 runCli() 完成。仓库在 bin.ts 末尾正是这样做的。

若从另一个 ESM 文件导入 main.mts，第一行变成 false。仓库同时使用 await import("./profile-boot.ts")。这是执行到某个分支时才加载的动态导入，解构出的 runProfile 是那个模块的命名导出。

2. 声明合并、模块扩充与空的 type import

同一个模块里的同名 interface 可以合并字段。declare module "模块名" { ... } 在已是模块的文件里扩充另一个模块的现有声明。下面先看同名接口的最小版本。

项目用它给 @deepseek-ai/cordis 的 Context 增加 tools、llm 等服务键，也用它给事件接口添加名字和参数。import type {} from "某包" 把该包的类型声明纳入检查，使扩充可见，发射的 JS 会擦除这一行。相反，import "某包" 会在运行时加载模块。某个属性在类型上可见后，运行时仍要靠 profile 装配服务。必需服务写进 inject，可选服务可通过 ctx.get("键") 查询并分支处理。

3. 类型与值可同名，品牌类型给 ID 分组

declare const BRAND: unique symbol 声明一个具有唯一类型身份的符号名字，本身不创建运行时变量。[BRAND] 在类型里作为计算属性键，与 string 交叉后便可区分两个原本都是字符串的 ID。该交叉只影响静态检查。仓库中 SessionId 同时可以在类型位置指类型，在 SessionId(raw) 中指函数。相同技巧也出现在 interface Config 和值 Config，一个供类型检查，另一个作为 Cordis 读取的配置 schema。

若传入一个静态类型是 JobId 的变量，检查器会拒绝。品牌转换自身无法验证字符串是否对应一个真实 Session，文件或网络输入仍由所属边界校验。读 SessionEvent<'turn/end'>['data']['reason'] 时，从左到右读：挑出某种事件 → 取它的 data 类型 → 再取 reason。

4. const 泛型与 NoInfer

<const T> 是类型参数的修饰符，让调用时直接写进去的对象和数组字面量优先保留精确值。它类似在调用处保留字面量信息。NoInfer<T> 仍接受 T，但提示检查器别从这个位置反推 T。先从模式或候选列表确定类型，再用它检查第二个位置。

DSH 的 defineTool 把参数 schema、返回 schema 保留到类型层。InferArgs<S> 从输入 schema 推出字段，InferValue<NoInfer<O>> 让回调按输出 schema 给定的类型工作。运行时另有 JSON Schema 校验。再遇到 asserts value is X 时，把它读成「函数正常返回后，检查器可将参数收窄为 X」，失败路径应抛错。

5. 同步生成器与可撤销的 effect

上一份讲过 async function*。这里的 function* 创建同步迭代器，调用函数先拿到迭代器，.next() 才推进到 yield。在 DSH 的 ctx.effect(function* (...) { ... }) 中，Cordis 接手推进并管理产出的清理函数。this: ToolsService 是 TS 的假参数，用来约束函数的接收者，调用者无需在实参中传入它。.bind(this) 则在运行时绑定接收者。

这个练习手动调用清理函数。真实 ctx.effect 会在所属 fiber 释放时处理登记的清理动作。ctx.on 也将监听绑定到生命周期。读代码时查两处：注册发生在哪个插件上下文，清理由谁负责。

6. @Remote、类型断言与配置里的表达式

@Remote('prompt') 是附在方法声明上的装饰器写法。读成「该方法标记为远程调用面的一部分，对外名字是 prompt」。在这个仓库中还要联系 Typert 的 Host 编译和生成步骤，以及 API Gateway 的路由。仅看这一行无法知道请求怎样传输、认证或分发。下面的 Web 旁路会跟到控制器和命令层。

invocation satisfies never 是类型穷尽检查。如果联合新增分支而 switch 忘记处理，默认分支的值就不再是 never。throw 仍负责实际执行时的失败。void run(...).catch(...) 表示刻意不等待该表达式的返回值，catch 负责处理拒绝。

cordis.patch.yml 是 YAML。- 开始列表项，缩进决定层级，id 指向配置中的行，name 指插件模块名或路径。!!js 是仓库 Loader 识别的 YAML 标签。它在允许的位置把值解释为表达式，如 task: !!js ctx.headlessStartup.task 会读取已注入服务的数据。普通 YAML 文本保持字面值。配置也可以改变插件是否挂载。

7. using 与 Symbol.dispose

using 声明一个需要在块结束时释放的资源。它和 const 类似地绑定名称，但作用域退出时会调用该值的 [Symbol.dispose]()，抛错离开时也会执行。[Symbol.dispose] 是用标准符号作为方法名。异步释放另有 await using 与 Symbol.asyncDispose。Web 命令层用 using binding 让附件绑定有明确的收尾位置，binding.commit() 则是业务确认，两个动作各司其职。

CHAPTER 02

DSH 的 Cordis 串讲

先搞懂插件如何找到依赖、什么时候执行，以及离开时谁负责清理，再看 DSH 怎样用配置把它们装在一起。

Cordis 是 DSH 仓库里自带的 TypeScript 插件框架，实现在 vendor/cordis。它解决的是应用组装问题。例如工具要注册到工具表，工具表可能又依赖系统提示词服务。Cordis 负责把这些组件挂起来、按服务依赖决定就绪时机、在它们之间传递事件，并管理卸载。模型请求、工具权限、对话历史这些业务规则仍由 DSH 各自的插件实现。

名字先怎么理解DSH 里怎么看
Plugin一块要挂载的代码。它可以提供服务，也可以贡献工具、监听器或配置。todo_write 的插件入口导出 apply(ctx, config)。
Context插件访问服务和注册能力的入口。传进 apply 的 ctx 带着当前插件和作用域的信息。ctx.tools、ctx.llm、ctx.sessions。
Service通过一个名字发布的能力。消费方使用这个名字和接口。通过 ctx.tools 获取工具注册表，通过 ctx.agents 请求创建 Agent。
Fiber某个插件实例的运行句柄，记录依赖、状态、子插件和清理动作。ctx.plugin(...) 返回 fiber，await fiber.dispose() 等它卸载完。
Effect一项与插件存续期绑定的注册或资源，同时记录如何撤销。注册的工具与事件监听随所属插件卸载。
Loader / Include把配置中的条目变成插件实例。Include 处理配置树和 patch，Loader 处理条目、解析与挂载。从选定的 profile 加载 YAML 条目，再交给 Cordis 核心管理生命周期。

1. 一个插件怎样提供服务，另一个怎样等它

下面直接调用仓库 vendored Cordis 做实验。完成本项目的依赖安装后，把示例存为仓库根目录的 scratch-cordis.mts，执行 pnpm exec tsx scratch-cordis.mts。示例只创建一个隔离的内存 Context，无需模型 API key。这里用代码挂载来观察机制，正式 DSH 的 Web 和 Headless 启动仍走 dsh profile。

读一遍这三个位置就能分清分工。declare module 是静态类型提示，super(ctx, 'greeter') 是运行时注册，inject: ['greeter'] 是启动和持续依赖。需要这个服务才能工作的插件声明 inject。服务缺少时仍可正常工作的功能可以查询 ctx.get('服务名')，再处理缺失分支。

2. 底层为什么能做到先等待、再运行

new Context() 会创建一个 Proxy，并安装服务解析、事件、插件注册等内建能力。Proxy 可以接管属性读取，所以 ctx.tools 看着像访问字段，实际可能根据当前 fiber 的注入和作用域找到服务实例。服务提供方通过 ctx.provide() 或 Service 基类登记，依赖方看到的是当前作用域可用的实现。

下一段是 Fiber 计算依赖是否可用的核心。它把当前修订和各服务实现的标识拼成 epoch。缺少必需服务时用 INACTIVE 表示当前绑定不能运行。实现被替换时标识会变化，Cordis 由此知道何时需要卸载旧绑定并重新加载。等待期间是 PENDING，执行插件时是 LOADING，成功后才到 ACTIVE。出错和主动卸载有各自的状态。

两个常见误会。YAML 行顺序决定配置如何组合，插件能否启动还要看依赖是否就绪。ctx 也有作用域。DSH 可以为一个 Agent 组合不同的服务，在隔离范围内让相同名字的服务指向不同实例。排查依赖时要看消费方自己的 ctx。

3. 卸载为什么能把工具和监听器也一起撤掉

ctx.effect(() => { ...; return dispose; }) 把注册和撤销绑定成一件事。插件自己的定时器、连接或 watcher 可以在这里建立，再返回关闭操作。ctx.on 已经内建这种机制，所以插件通常直接注册事件。看底层实现，真正保存在 fiber 上的是一个负责登记监听、并返回取消登记函数的 effect。

DSH 的工具注册也有类似的所有权。前面的服务实验卸载了 provider，消费插件随之清理。第 07 章的 todo_write 测试则直接验证，释放贡献工具的 fiber 后，ctx.tools.schemas() 中就找不到该工具。需要有序清理多个资源时，可以把它们放进一个 disposer，按顺序等待。

4. 服务是直接调用，事件用来通知或拦截

想做一件明确的事时，调用服务方法，例如 ctx.tools.execute(...)。想观察已经发生的事，可监听 session/event。想在原动作前后插入策略、审批或包装，先找这个扩展点定义的事件模式。

调用方式顺序与返回
ctx.emit(...)同步通知监听器，不等待它们返回的 Promise。常用于发送观察事件。
await ctx.parallel(...)并发调用监听器，并等它们全部结算。
await ctx.serial(...)逐个调用并等待，遇到符合约定的返回值时停止。
ctx.bail(...)同步检查监听器，遇到符合约定的返回值时停止。和 serial 一样，undefined、null、false 不会触发停止。
ctx.waterfall(..., fallback)把监听器套在默认动作外面。监听器调用 next() 才继续，可以包装返回值，也可以提前结束。异步链由调用者等待。

这和 DSH 的 tools/pre-execute 是同一种结构。工具管线提供默认的 allow，插件监听器可以选择委托给下游，或按约定返回 ask、deny 等决定。ask 会走审批服务，最终 guard 和取消检查仍由 DSH 自己处理。只做记录的监听器应继续调用 next()。Cordis 的实现还会拒绝同一监听器重复调用 next()。

5. Loader 怎样把 DSH 配置变成插件树

把 profile 当成某种应用的装配方案。bundle 是可组合的一层条目，patch 按 id 修改已有条目或插入新条目。组合后的每个条目告诉 Loader 到哪里找插件、给它什么配置、它还要等哪些服务。DSH 的 boot() 创建根 Context、安装 Loader、提供启动环境，最后通过 Include 挂载配置树。下一章的架构图和启动章会再把这条链画出来。

以 Headless 为例，headless-startup 解析命令行，通过 ctx.provide 发布名为 headlessStartup 的服务。另一个 YAML 条目声明要注入该服务。配置里的 !!js 会等到目标条目的依赖就绪后，在对应上下文里求值。任务字符串由此从命令行到达 Runner。

6. 下次看到 DSH 插件，按这个顺序读

  1. 在 bundle 或 overlay 查 id 和 name，确认这个条目由哪种 profile 挂载。
  2. 在模块入口查 inject 与 apply。它是提供一个服务，还是给现有服务注册工具、监听器或其他贡献？
  3. 从消费方的 ctx.服务名 或事件名反查 provider、事件声明和分发位置。类型声明和运行时注册分别看。
  4. 最后查清理。找 ctx.effect、ctx.on 或已封装生命周期的注册方法，再看对应的卸载测试。
自测 · 为什么我的插件在配置里有一行，apply 却没打印？

先用配置输出确认该条目确实存在且启用，再查模块路径和启动诊断。若状态是 PENDING，重点看 inject 里的每个服务是否在该作用域可用。配置里有条目、模块加载完成、服务依赖就绪、apply 成功结束，是四个不同的检查点。

架构与项目地图

从用户入口找到组装层，再找到处理请求、执行工具和保存会话的代码。

DeepSeek Harness（下面简称 DSH）把模型、工具、Agent 循环、会话存储和应用入口装进同一棵 Cordis 插件树。先找组装配置，再找调用点。 看到一个包存在，只能确定它提供了实现。它在哪个应用里实际启用，由选中的 profile 及其 patch 决定。

用包名反查源码

这里是 pnpm monorepo。packages/<组>/<包> 是目录，@deepseek-ai/dsh-* 是跨包导入的名字，二者未必同形。例如 @deepseek-ai/dsh-tools 位于 packages/core/tools。同包源码写 ./schema.ts。workspace:* 和 workspace:~ 是 pnpm 工作区依赖声明。源码检查通过 tsconfig.base.json 的 paths 找到 src。构建产物的入口则看包的 exports，例如 headless 的 . 与 ./startup 分别指向两个 lib 文件。

服务调用 · 要一个能力ctx.tools.register(...) 往工具服务注册定义。ctx.agents.create(...) 从 Agent 注册表请求实例。

CHAPTER 05

顺着源码追 CLI 和插件挂载

以 pnpm dsh --profile headless 为例，先看到参数如何变成一次可启动的配置组合。

1. 从命令参数到分支

process.argv 的前两项是 Node 和入口路径，slice(2) 得到用户传的部分。parseDshArgs 返回带 mode 的联合。普通启动走 profile，再动态导入 runProfile。--dump-config 切到单独的配置输出分支。第一个摘录里的 StartupError 分支负责输出启动故障，其他异常继续向外抛。

2. 先提供进程事实，再挂应用

外层 boot(..., async (hostCtx) => { ... }) 最后传入一个准备函数。它把 profile 数据、启动环境和命令行/退出请求交给 Host Context。插件随后从 Context 取这些事实，读取同一份启动配置。app.current 使启动期间的信号也能找到当前树，信号和清理链仍由启动器拥有。

new Context() 在该函数前面创建根。Loader 挂上后先 prepare，再挂根 Include，等待 Loader 的挂载结算并检查启动项。await prepare?.(ctx) 表示没有传准备函数时跳过调用。

3. Profile 叠加决定最终树

正常层次从低到高是 bundle 列表 → profile 自己的 patch → Harness home 的 patch → 命令行 overlay。这段代码还会按条件在尾部加遥测覆盖。...数组 把各层的行依次展开。同一个 id 上的 config 替换应视为整块配置替换，不能假定会递归合并。修改前先看 --dump-config 的最终行。

Headless 基于共享 base，再插入 headless-startup 与 headless-runner。回到第一章的 YAML 摘录，前者提供 headlessStartup，后者从它读取任务与选项。Web 选择另一套应用层，其中的 webserver 行决定监听地址。它们继续共享 Agent 和 Session。

CHAPTER 06

从任务字符串追到模型流

读清 Agent、Turn、Step 和 Tool Call 的层次，再看它们如何接起来。

名词这里是什么意思观察点
Agent当前进程中的运行对象，持有 inbox、状态和执行能力。ReactLoopAgent 实现 Agent。
Session身份和有序事实，可能在另一次进程启动后恢复。session.append(...) 写逻辑事件，deriveMessages() 产生模型历史。
Turn从开始接手工作到本轮收束，可包含零个或多个 step。turn/start、turn/end。
Step一次模型请求及其关联工具执行。被拒绝或初始输入被改写为空时可以没有 step。step/start、step/end，中间有 assistant 结果和 tool 结果。

1. Headless 把 prompt 放进 inbox

run 按 sessionId 选择创建 Agent 或接管确切的既存 Session。AgentLoop 在安装时给 ctx.agents 设置 factory，注册表因此能调用默认的 Agent 实现。最终传给 followup 的是结构化用户消息。

顺着 followup 进入 send，消息插入 inbox 后唤醒 driver。steer 以 next-step 为目标并唤醒。inject 也以 next-step 为目标，传 false 所以单独注入上下文不会唤醒 idle Agent。上面的 runner 等待 Agent 和关联子任务稳定，刷新 Session，再从事件摘要写最终文本或结束 JSON 投影，并请求进程按完成原因退出。

2. 开启 Turn，审查下一 Step

先追加 turn/start，再从 inbox 处理下一批输入。preStep 会走 agent/pre-step waterfall，监听器可以接受、重写或拒绝。拒绝时收束为 blocked；第一次接受的输入为空时可以直接结束。这两条分支都先于 step/start。真正进入 step 后，才准备模型调用。

3. 绑定适配器，用日志重建请求，消费流

默认 base 把 llm-deepseek 行指向 API key 插件。它把 DeepSeek provider 注册到 ctx.llm。Loop 拿到选定 provider/model 后通过 prepareCall 绑定适配器，再构建本次请求。区分三个入口有助于定位故障：

  • 凭据或 provider 安装。packages/llm/llm-deepseek-api-key/src/index.ts
  • 适配器登记和通用模型接口。packages/llm/llm-deepseek/src/host.ts；packages/llm/llm/src/index.ts
  • DeepSeek 请求与流解析。packages/llm/llm-deepseek/src/adapter.ts

session.deriveMessages() 读到本次可见的历史。请求对象同时带上工具历史、工具声明、Session 身份和取消信号。条件展开 ...header.tools !== undefined ? { tools: header.tools } : {} 可在心里加括号读成 ...(条件 ? 有字段的对象 : 空对象)。随后对流逐块 for await，同时检查取消信号。

4. 模型要求调用工具时

先结算完整的 assistant/message，再从内容块中找 type === "tool-call"。没有工具调用，这条路径完成。存在工具调用，则把调用数组、Agent、取消信号、turn/step 和并发限制交给 ctx.tools.execute。若工具批次还需要模型继续，返回 null 交由外层继续调度。finally 会在该 step 收尾写入 step/end。失败或取消的 assistant 尝试还可能结算为 assistant/attempt，见同一文件的错误分支。

自测 · 为什么只看到 turn/start 也可能是正常路径？

preStep 拒绝或首次重写为空时，可以从 turn/start 收束到 turn/end，没有 step/start。如果连结束事件也没有，再去检查异常和中途退出。

CHAPTER 07

精读 todo_write · 一个工具如何进入系统

用真实注册、schema、执行结果和测试理解扩展点。

todo_write 一次替换整个清单。Base YAML 中的 id: tool-todo 把包挂上。入口声明依赖 tools 和 sessionProjections，在 apply 内注册投影和工具。项目中的品牌 ID、可配置策略、结构化返回值在这一条路径上都能看到。

把输入模式、业务动作、输出模式和文字分开

  1. 输入：parameters.todos 规定数组、项目结构和允许的状态。defineTool 同时用它推导 args 类型，并为模型传入的 JSON 做运行时校验。
  2. 业务检查：toTodoList 清理并验证内容，allowParallelInProgress 控制允许几个进行中的事项。exec.agent 指这次调用的所有者。没有 Agent 就无法把清单写入所属 Session，因此抛出错误。
  3. 结构化结果：execute 写 todo/write，返回 todos 和 counts。output.schema 描述这个返回值。
  4. 模型可见内容：output.render 把返回值投影成文本块，工具管线据此产生 tool result。网页卡片是另一个呈现面。

工具管线从 tools/pre-execute 做准入，tools/execute 包裹实际分发，tools/post-execute 处理结果策略。若要计时或观察，使用对应扩展点并在应该委托时调用 next()。若修改权限策略，应在它所属的 guard 或前置钩子处理。三个调用点都在 packages/core/tools/src/pipeline.ts。

register 最终把定义放进当前层的 effect，返回 disposer。挂载和卸载测试验证了同一个 registry：挂上工具时 schema 可见，释放 fiber 后不可见。

先把预期结果写得具体

这个测试给两项，分别处于 in_progress 和 pending。它同时检查三个出口：程序值中的计数、文本里的计数、所属 Session 的 todo/write。这比只检查 execute 返回成功覆盖更多真实行为。

CHAPTER 08

Session 记录、投影与 Web 旁路

区分实时 chunk、已提交事件、模型历史，以及 Web 入口如何抵达同一个 Agent。

1. 从仓库录制的结果倒读

这里可以直接打开实际录制的 snapshots/session/todo-write/session.v4.jsonl。下列几行来自同一份文件。日志用于说明真实事件数据的形状，和上一章单元测试的两项输入分别来自不同用例。

todo/write 是清单的领域事实。tool/result 内有一条模型可见的工具消息，录制的文字是 Updated todo list: 1 pending, 2 in progress, 0 completed.。turn/end 给出该轮结束原因。相同 Session 里的 agent/assistant-stream 是进程内的实时事件通道；已经结算的 assistant 消息或尝试会有自己的耐久事件形状。实时 UI 可以先看到 chunk，持久历史根据结算事件恢复。

一份日志，可派生两种不同读法

模型历史 · Session.deriveMessages沿 surface 的序号读取能生成消息的事件。尾部追加可以增量派生，出现替换等代次变化时重建缓存。
待办 UI 状态 · todos 投影在 todo/write 时采用最新完整列表，下一次 turn/start 清空，其他事件保留当前状态。

不是每条事件都属于模型消息历史。todo/write 用于领域投影，而带对应 surface 操作的 tool/result 可进入模型历史。改变模型所见内容需要保留可重建的日志事实。保存到磁盘、识别版本、迁移历史代次属于持久化 provider。做第一次扩展时先用已有事件与结构，碰到格式或迁移再读 docs/session-format-status.md。

2. Web 用不同入口，复用 Agent

控制器校验边界数据后把请求交给命令层。命令层完成附件输入的准入并检查 Agent 仍然存在，按模式选择 steer 或 followup。这里的 using binding 把附件绑定资源的生命周期限制在块内。成功走 commit()，退出作用域时仍走资源的 dispose 契约。Web 请求的接受回执与最终助手答复是不同阶段。追回传时可继续查 SessionController 上的 page 和 stream Remote，或从 docs/api-gateway.md 跟路由和生成的 Remote 声明。

第一道真实改动练习

选一个小的 todo_write 行为，从需求写到测试。例如「输入内容两端空白时，存下修剪后的文本」。打开 packages/todo/tool-todo/tests/tool-todo.spec.ts，先找已有的 trim 测试，再反查 toTodoList。随后为你的变体补一条有意义的边界用例。若变更模型看到的文本，检查录制 Session 中的 tool/result，以仓库测试策略决定应更新的 snapshot。Session 格式和核心循环都有更广的兼容性要求，第一次扩展适合落在已有插件契约上。

上面的回放命令适用于已按开发文档完成准备的环境。若看到零个测试匹配，检查 -t 传参和场景名。回放配置在 vitest.snapshot.config.ts，测试驱动在 snapshots/session/headless.snapshot.ts，测试分层在 docs/testing.md。涉及打包后的入口，再选对应 built smoke；Provider 的真实 API e2e 单独用凭据执行。提交前按 AGENTS.md 的改动范围选择检查。

下一次读源码时的顺序

  1. 写下你要观察的输入和结果，例如 todo_write 的两个状态计数。
  2. 用配置找到行的 id 和模块 name，打开对应 package.json 与实现。
  3. 追实现入口的 inject，分别定位服务定义、provider、调用者。定位到一个方法后，再查它的调用和测试。
  4. 标记模型所见、UI 所见、Session 所存各属于哪个出口。改动后到对应的结果处验证。
